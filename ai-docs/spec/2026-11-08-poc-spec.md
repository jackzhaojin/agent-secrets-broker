# Agent Secrets Broker: Proof of Concept Spec

Owner: Jack. Drafted Nov 8, 2026. Status: baseline POC, not production.

## 1. Outcome

A small service that holds my secrets (API keys, OAuth refresh tokens) and makes API calls **on behalf of** my agents. Agents never receive a secret. They connect to the broker as a remote MCP server, sign in with OAuth, and can only call the tools their policy allows.

One sentence test: *Claude Duet asks the broker to do something that needs an API key, gets the result back, and the key never appears anywhere Duet can see.*

## 2. Why (the constraint that drives the design)

Agents differ a lot in how they can hold secrets:

| Agent | Can hold a secret? | How it can use the broker |
|---|---|---|
| Claude Duet | **No.** No vault. Will not accept keys or tokens pasted in chat. Anything a tool returns lands in its context, so it cannot "fetch and not read". | Custom connector (remote MCP) with OAuth handled by the app. This is the design target. |
| Grok Bot | Has its own Vault, but logins and cards only, Grok Bot only, no API or audit log. | Remote MCP if supported (verify), or its own vault for logins. |
| AnimaMesh (mine) | Yes, it is my code. | MCP client or plain HTTPS with a client credential. |
| Others (Muse, Dots) | Unknown. | Verify MCP support later. Out of POC scope. |

**Design rule:** build for the most restricted agent (Duet). If Duet works, everything else is easier.

## 3. Duet's limits the POC must respect

1. Duet never sees a raw secret. Tool responses must never contain a key, token, or credential, including in error messages.
2. Duet does not handle tokens itself. The Claude app runs the OAuth flow when I add the connector in settings and stores the token. Duet only calls tools.
3. Duet's connector traffic comes from Anthropic's cloud, so the broker must be reachable on the public internet over HTTPS (not localhost, not my laptop).
4. Anything returned is visible to the model, so return only what the task needs (shape and trim responses).

## 4. Architecture

```
 Agent (Duet / AnimaMesh / Grok Bot)
        |  MCP over HTTPS + OAuth access token (short-lived)
        v
 +--------------------------------------+
 | Agent Broker (remote MCP server)     |
 |  - OAuth 2.1 authorization server    |
 |  - Policy: which client -> which tool|
 |  - Tool handlers (call upstream APIs)|
 |  - Audit log                         |
 +--------------------------------------+
        |  fetch secret at call time (cached briefly in memory)
        v
 1Password vault "Broker" (read-only service account)
        |
        v
 Upstream API (e.g. GitHub, OpenWeather, Google)
```

Key points:
- Secrets live in 1Password, not in the broker's code or database. The broker holds only the 1Password service account token (as a platform secret / env var).
- Each agent is a separate OAuth client. Its access token maps to a policy entry.
- Tools are task-shaped (`github_list_my_repos`), not generic (`get_secret`). There is **no tool that returns a secret**.

## 5. Baseline POC (must have)

Scope is deliberately tiny: one secret, one upstream API, two tools, one agent (Duet) end to end.

### 5.1 Components
1. **Remote MCP server** using the official MCP TypeScript SDK, Streamable HTTP transport, served over HTTPS.
2. **OAuth 2.1** per the MCP authorization spec:
   - Protected Resource Metadata (`/.well-known/oauth-protected-resource`)
   - Authorization Server Metadata (`/.well-known/oauth-authorization-server`)
   - Dynamic Client Registration (so the Claude app can register itself)
   - Authorization code + PKCE, short-lived access tokens (15 min), refresh tokens
   - Consent page where **I** log in (simple: single hard-coded owner, password or passkey; or delegate login to GitHub OAuth) and approve the client
3. **Secret fetch** from 1Password using a read-only service account scoped to one vault named `Broker`.
4. **Two tools**:
   - `whoami`: returns the calling client's name and its allowed tools. No upstream call. Proves auth and policy.
   - `github_list_my_repos` (or any one API you prefer): fetches the API key from 1Password, calls the upstream API, returns a trimmed list (name, url, updated). Proves the full path.
5. **Policy file** (`policy.json`): client name -> allowed tools.
6. **Audit log**: one line per tool call (time, client, tool, success/fail). Never log secrets or full upstream responses.
7. **Revoke**: a way to kill a client's tokens (admin endpoint or CLI) and see the next call fail.

### 5.2 Suggested stack (TypeScript)
- Option A (fastest to public HTTPS): **Cloudflare Workers** with Cloudflare's `workers-oauth-provider` library and its remote MCP server template. Verify the 1Password JS SDK runs in Workers (it uses WASM). If not, call 1Password via a tiny Node sidecar or use Option B.
- Option B (most familiar): **Node + Express** on Azure Container Apps / Fly.io / Render, MCP TypeScript SDK, and a small OAuth server (e.g. `oidc-provider`) or a hosted IdP (Auth0, WorkOS, Stytch) that supports DCR.
- Secrets SDK: `@1password/sdk` with `OP_SERVICE_ACCOUNT_TOKEN` stored as a platform secret.

### 5.3 Acceptance tests (the POC is "proven" when all pass)
1. **Connect:** In the Claude app, add the broker URL as a custom connector. The OAuth consent page appears, I approve, the connector shows connected.
2. **Auth works:** Duet calls `whoami` and gets back its client name and allowed tools.
3. **Do something real:** Duet calls `github_list_my_repos` and gets a trimmed repo list.
4. **No leak:** search the full tool response, error responses, and audit log for the key's value: zero matches. Force an upstream error (bad key in 1Password) and confirm the error text has no secret.
5. **Policy:** remove `github_list_my_repos` from Duet's policy. The tool call is refused (or the tool is not listed).
6. **Revoke:** revoke Duet's client. Next call fails with 401, and reconnecting requires my consent again.
7. **Rotation:** change the key in 1Password only. Next call uses the new key with no redeploy.

### 5.4 Out of scope for the baseline
Multiple owners, UI dashboards, agent-to-agent delegation, per-call human approval, storing OAuth refresh tokens for third-party sites, browser login filling.

## 6. Phase 2 (only after baseline passes)
1. **Second agent:** AnimaMesh as its own OAuth client (client credentials grant) with a different policy. Prove Duet cannot call AnimaMesh's tools and vice versa.
2. **Upstream OAuth:** broker holds a refresh token for one Google or GitHub OAuth app, refreshes access tokens itself, never returns them.
3. **Per-call approval:** sensitive tools pause and send me an approve/deny prompt (push or email link) before running.
4. **Key notes:** read purpose, expiry, risk and rotation fields from each 1Password item; a `secrets_inventory` tool returns metadata only (never values) so an agent can remind me about expiring keys.
5. **Agent-to-agent grants:** one agent can request a time-boxed, narrower grant for another agent, approved by me.
6. **Grok Bot:** test whether it can use a remote MCP connector.

## 7. Security rules (non-negotiable even in POC)
- No tool returns a secret, token, or credential. No `get_secret` tool, ever.
- Never log request bodies that might contain tokens, or full upstream responses.
- Access tokens short-lived; refresh tokens revocable; PKCE required.
- 1Password service account is read-only, one vault, with an expiry date.
- Use a throwaway or low-risk API key for the POC (e.g. a fine-grained GitHub token with read-only repo metadata).
- HTTPS only. Validate `redirect_uri` exactly against registered values.

## 8. Things to verify while building (I have not confirmed these)
- Exact OAuth requirements the Claude app's custom connectors expect today (DCR vs Client ID Metadata Documents, required metadata endpoints, callback URL). Check Anthropic's current custom connector docs first.
- Whether Claude Duet in my account can add a custom connector directly, or whether it is added in claude.ai settings and then shows up in Duet.
- 1Password JS SDK compatibility with Cloudflare Workers, and service account rate limits on the Individual plan (reported around 1,000 reads a day, so cache values for a few minutes).
- Whether Grok Bot, Muse or Dots can use remote MCP servers.

## 9. Deliverables from the POC session
- Repo with the broker, `policy.json`, README with deploy steps.
- Deployed HTTPS URL.
- A short test log showing each acceptance test passing.
- Then tell Duet (personal-agents channel) the URL is connected, and Duet runs tests 2 to 4 itself.
